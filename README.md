[![hexlet-check](https://github.com/i-samsonov/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/i-samsonov/ai-for-developers-project-387/actions)

Интегрируйте работу агентов в GitHub проект

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Стек

- React, TypeScript, Vite
- Tailwind CSS, shadcn/ui
- Fastify (API), Vitest (тесты), Oxlint (линтер)

## API-контракт

Рукописный источник контракта — `api/main.tsp`. Выполните `npm run generate:api`, чтобы обновить OpenAPI (`generated/@typespec/openapi3/openapi.json`), типизированный клиент (`src/generated/sdk/`) и серверные типы, JSON-схемы валидации и регистрацию маршрутов (`server/generated/`). Эти артефакты не редактируются вручную. `npm run check:generated` проверяет повторяемость генерации и выполняется в CI после lint → test → build.

Серверные маршруты подключаются через `registerCalendarRoutes(app, handlers)`; генератор никогда не перезаписывает бизнес-логику. Все шесть операций доступны. Админский API не защищён авторизацией: приложение предназначено только для локального учебного использования, не размещайте его публично с реальными персональными данными.

## Установка

Рекомендуется Node.js 22.18+ и npm (при установке на Node.js 22.12 часть зависимостей предупреждает о несовместимой версии). По умолчанию API хранит данные в `calendar.sqlite` (SQLite, файл исключён из Git); путь можно изменить через `DATABASE_PATH`.

```bash
git clone https://github.com/i-samsonov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
npm install
```

## Использование

Запустите фронтенд и API в двух терминалах:

```bash
npm run dev
npm run dev:api
```

Откройте адрес, который выведет Vite (обычно http://localhost:5173). Vite проксирует `/api` к http://127.0.0.1:3000; если API запущен с другим `PORT`, задайте тот же `PORT` при старте Vite. Vite обновляет страницу при изменениях кода, а `tsx watch` перезапускает API. Остановить серверы можно сочетанием Ctrl+C.

Проверки и просмотр собранной версии локально:

```bash
npm run lint
npm test
npm run build
npm run check:generated
npm run preview
```

`npm run preview` поднимает локальный сервер для фронтенда из `dist/`. После сборки `npm run start:api` запускает Fastify, который отдаёт фронтенд из `dist/`, API по `/api` и проверку здоровья по `/health` на одном порту (по умолчанию 3000, либо из `PORT`).

## Docker и деплой

Работающее приложение из первого проекта: https://calendar-calls-386.onrender.com (проверка `/health` возвращает HTTP 200).

```bash
docker build -t calendar-calls .
docker run --rm -e PORT=8080 -p 8080:8080 calendar-calls
```

Откройте http://localhost:8080 и http://localhost:8080/health. Контейнер слушает `0.0.0.0` и использует `PORT`, переданный платформой. Файл базы по умолчанию хранится в `/data/calendar.sqlite`; без подключённого постоянного тома данные теряются при пересоздании контейнера. Для постоянного хранения подключите том к `/data` или задайте `DATABASE_PATH` на путь в смонтированном каталоге.

Проверки запускаются также в GitHub Actions (`.github/workflows/ci.yml`). Файл `.github/workflows/hexlet-check.yml` отвечает за отдельные проверки Хекслета.

## Агент в GitHub

В комментарии к issue или PR можно упомянуть **`/oc`** или **`/opencode`** — запустится [OpenCode GitHub Action](https://opencode.ai/docs/github/) (`.github/workflows/opencode.yml`). Пример:

```text
/oc explain this issue
```

Запускать агента могут только авторы с ролью `OWNER`, `MEMBER` или `COLLABORATOR`; комментарии остальных и ботов игнорируются. Модель — `opencode/big-pickle`, ключ берётся из секрета Actions **`OPENCODE_API_KEY`** (OpenCode Console). Сессии не публикуются (`share: "false"`): доступны только прогон Actions и ответ в issue. Секрет **`HEXLET_ID`** относится к проверкам Хекслета и не связан с агентом.

Workflow аутентифицируется через [OpenCode GitHub App](https://github.com/apps/opencode-agent): OIDC-токен обменивается на установочный токен App, поэтому права на комментарии и PR выдаёт само приложение, а у workflow остаётся `contents: read`.

### Лимит ручных запусков в PR

Для `/oc` и `/opencode` в обсуждении PR и комментариях к строке diff установлен общий предел **3 допущенных попытки на PR**. `.github/workflows/opencode.yml` проверяет его до вызова модели: бюджетный скрипт исполняется из доверенной основной ветки, а после допуска агент получает точный head SHA PR. Скрипт по истории запусков этого workflow в Actions (с учётом `run_attempt`) считает шаги `Budget admitted` для данного PR. Отмена, тайм-аут, ошибка агента и повторный запуск уже допущенной попытки расходуют бюджет; отсутствие ключа до допуска и отказ `limit_exhausted` новую попытку не расходуют. Запуски для одного номера PR сериализованы. Проверка опирается на сохранённую историю Actions и конфигурацию workflow; администратор репозитория может изменить эти условия, а новый PR получает новый бюджет. Форки исключены из ручных вызовов модели.

Отдельное задание без модели публикует в PR причину (`limit_exhausted`, `timeout`, `infra` или `agent_failed`), текущий head SHA и ссылку на логи со статусом «нужен человек». Оно получает `pull-requests: write`; агенту по-прежнему не передаётся токен этого задания. После исчерпания бюджета человек пересматривает подход или завершает правку сам, автоматического цикла исправлений нет.

### Независимое авторевью PR

Авторевью состоит из двух workflow. `.github/workflows/opencode-review.yml` запускается на `pull_request` при создании, обновлении и повторном открытии PR и при снятии статуса draft: регистрирует событие **без checkout, модели, секрета и прав записи**. После успешного завершения `.github/workflows/opencode-review-publish.yml` запускается на `workflow_run` из основной ветки. Он перепроверяет текущий head SHA и автора PR через GitHub API; устаревшие и fork-запуски не получают секрет. Checkout выполняется только для доверенного `main`, критерии `REVIEW.md` берутся из Git-объекта этой ветки (только обычный файл), head PR загружается **только как объекты для diff**, его код не запускается. Ревьюер читает diff, описание PR, связанные issue и статусы CI, но не правит файлы. CLI устанавливается до checkout и вне его каталога, затем запускается без GitHub-токена и с запретом инструментов изменения; отдельное задание публикует итог как GitHub review, привязанное к проверенному SHA. Замечание авторевью само по себе не запускает исправление: человек разбирает его и при необходимости вызывает `/oc` в PR.

Секрет модели доступен только PR в `main` из веток этого репозитория от владельца, участников с ролью `OWNER`/`MEMBER`/`COLLABORATOR` и доверенных ботов OpenCode App или GitHub Actions. PR из fork пропускаются; при изменении списка доверенных ботов проверьте их точные логины. Ревью имеет тайм-аут 15 минут; новое событие для той же ветки PR не отменяет уже выполняющийся запуск, а ожидает завершения; устаревший SHA повторно проверяется перед публикацией. Подготовка контекста использует `contents: read`, `issues: read`, `actions: read`, `checks: read`, `statuses: read`, `pull-requests: read`; отдельное задание публикации получает только `pull-requests: write`. Для запуска нужен существующий секрет `OPENCODE_API_KEY`. Ревью может стартовать одновременно с CI и не увидеть его окончательный результат; перед мержем человек сверяет результаты CI и head SHA. Шаблон `.github/pull_request_template.md` требует ссылки на согласование, проверки, оценку риска и способ отката. Доверенный workflow на `workflow_run` начнёт работать после мержа в `main`: исходный PR нельзя считать его live-проверкой, поэтому решение о начальном мерже принимает человек по коду и CI. Если PR создан через `GITHUB_TOKEN`, GitHub может ожидать подтверждение запуска `pull_request` workflow человеком; проверьте это в Actions.

Для PR, созданных release-please через `GITHUB_TOKEN`, GitHub может не создать последующий `workflow_run` после подтверждённого `pull_request`-запуска. Доверенный reviewer также слушает завершение `release-please` на актуальном `main`: проверяет **каждый** подходящий release-PR, а не только первый, но **вызывает модель только при успешном `PR review context` на точном head SHA** PR из этого репозитория, созданного `github-actions[bot]` в release-please-ветке. Если GitHub потребовал одобрения первого этапа уже после завершения release-please, вручную запустите `Independent PR review` через Actions → Run workflow на ветке `main`, указав `pr_number` и ID успешного `PR review context` в `context_run_id`. При обновлении release PR сначала подтвердите новый context run и используйте его ID. Ручной запуск не обходит проверку совпадения PR, актуального `main`, успешного первого этапа и head SHA; повторный запуск для уже проверенного SHA не создаёт дублирующее ревью. Опубликованным считается только отзыв бота со статусом `COMMENTED` или `APPROVED`; `PENDING` и `DISMISSED` не блокируют повтор. Все пути ревью release-PR сериализованы до публикации (включая обычный `PR review context`); GitHub хранит только один ожидающий запуск в concurrency-группе, поэтому после нескольких одновременных событий проверьте наличие ревью на актуальном SHA и при необходимости повторите ручной запуск.

Ручной запуск читает указанный `context_run_id` напрямую через GitHub API (в том числе после позднего подтверждения Actions), проверяет путь workflow, событие, результат, репозиторий и head SHA. Номер PR сверяется с данными run; если GitHub не указал связанные PR, используется API связи коммита с PR. Отфильтрованный список запусков нужен только автоматическому пути. Для автоматического `workflow_run` тоже проверяется путь файла, а не `name`: у `PR review context` задан динамический `run-name` вида `review-context-PR-14`.

### Автотриаж входящих обращений

`.github/workflows/opencode-triage.yml` запускает предварительный разбор **при создании issue** без команды `/oc`. Запуск доступен только для обращений от владельца репозитория и авторов с ролью `OWNER`, `MEMBER` или `COLLABORATOR`; обращения остальных авторов не отправляются модели. Тикеты и спецификации с меткой `ready-for-agent` (а также `ready-for-human` и `wontfix`) пропускаются. Подготовленные тикеты создавайте сразу с меткой `ready-for-agent`, иначе событие открытия запустит их разбор.

Инструкция агенту находится в `prompt` workflow: он сверяет обращение с текущим приложением, оставляет вопросы при нехватке данных и рекомендует следующий шаг, но не меняет код и не начинает реализацию. Для меток используются правила из `docs/agents/triage-labels.md`; вопросы переводят обращение в `needs-info`. Триаж ограничен десятью минутами, а запуски по одному issue выполняются последовательно с ручным `/oc`.

Автотриаж использует встроенный `GITHUB_TOKEN` с правами `contents: read` и `issues: write`, чтобы агент мог прочитать репозиторий и оставить комментарий или метку. Ручной `/oc` по-прежнему использует GitHub App. Ответы на вопросы и согласование спецификации и тикетов остаются за человеком; создание issue с меткой `ready-for-agent` само по себе не запускает реализацию.

### Ежедневный аудит страницы

`.github/workflows/scheduled-audit.yml` запускается ежедневно в **03:17 UTC (06:17 по Москве)** и вручную через **Actions → Scheduled page audit → Run workflow** из ветки `main`. Расписание GitHub может задерживаться или пропускаться. В настройках репозитория задайте **Settings → Secrets and variables → Actions → Variables → `APP_URL`** — публичный адрес проверяемой страницы (например, `https://calendar-calls-386.onrender.com`). Аудит использует `opencode/big-pickle` и секрет Actions **`OPENCODE_API_KEY`**; наличие секрета проверяется до вызова модели, но доступность баланса OpenCode Console этой проверкой не подтверждается. `DEEPSEEK_API_KEY` аудиту больше не нужен. Не записывайте ключ в Git или текст задачи. При отсутствии ключа агент не вызывается, а причина сохраняется в выводе прогона. При отсутствии адреса или недоступности страницы отчёт обозначает «нет данных», а не «проблема исправлена».

В режиме `live` workflow собирает Lighthouse JSON; в ручном режиме `demo` создаёт **явно учебный** отчёт с одной симулированной находкой, не подтверждённой на сайте. Отчёты остаются на runner, не коммитятся, и сохраняются в артефакте **`page-audit-report`** на странице прогона на 30 дней. OpenCode читает отчёт, ищет совпадающие открытые и закрытые Issues и создаёт отдельную задачу только по новой находке; повторный `demo` с тем же идентификатором не должен создать дубль. Итог агента находится в **Summary** прогона, логах шага **Analyze and publish finding** и артефакте **`page-audit-conclusion`** (30 дней). Issue должен содержать суть проблемы, действие, адрес приложения и ссылку на прогон: после удаления артефакта эти сведения остаются доступны. Агенту доступны только чтение репозитория и запись Issues через `GITHUB_TOKEN`; код и PR он не меняет, реализацию решает человек.

**Результаты проверки:** [первый ручной `demo`](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43505621453) сохранил отчёт, но завершился по тайм-ауту: OpenCode Console ответила `402 Insufficient balance`, а чтение отчёта вне рабочего каталога запросило интерактивное разрешение. После переноса отчёта в игнорируемый `audit-reports/` и восстановления доступа к модели [успешный `demo`](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43576044619) сохранил отчёт и вывод агента, который создал [учебную задачу #22](https://github.com/i-samsonov/ai-for-developers-project-387/issues/22). [Повторный `demo`](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43576161407) сохранил отчёт и вывод «дубль #22»: новая задача или одинаковый комментарий не появились. Отчёты обоих успешных прогонов доступны как `page-audit-report`, выводы — в Summary и `page-audit-conclusion` соответствующих прогонов. [Первый ручной `live`-прогон](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43577474631) собрал настоящий Lighthouse JSON для `APP_URL` (performance 100, accessibility 95, best practices 96, SEO 90), но агент получил `402 Insufficient balance` и позднее завис на разрешении записи черновика в `/tmp`. [Второй `live`-прогон](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43579329933) снова собрал отчёт, но агент получил `402` и завис при попытке удалить ошибочно созданный файл из `/tmp`. Оба live-прогона истекли по тайм-ауту: опубликованного вывода и issue по реальной находке нет. После переключения на DeepSeek и добавления секрета `DEEPSEEK_API_KEY` этот сценарий требуется проверить снова.

**Проверка DeepSeek:** [первый запуск с DeepSeek](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43583340332) не узнал `deepseek-v4-flash`; установленный Action предложил `deepseek-flash`. После исправления ID [следующий запуск](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43583578378) сохранил Lighthouse-отчёт, но DeepSeek отклонил ключ с HTTP 401. [Проверка авторизации перед запуском](https://github.com/i-samsonov/ai-for-developers-project-387/actions/runs/43583870794) подтвердила 401 и сохранила причину сбоя без вызова агента. Поэтому для новых запусков аудита возвращены `opencode/big-pickle` и `OPENCODE_API_KEY`; успешный `live`-прогон после возврата ещё не подтверждён.

**Вывод из прогонов:** успешный сбор отчёта не означает успешной работы агента. Для запуска без человека отчёт должен быть доступен в рабочем каталоге агента, а у провайдера модели должны быть действительные ключ и баланс. Явная пометка учебного режима и стабильный идентификатор находки помогли агенту не выдавать симуляцию за дефект и не создавать дубль. **Личные выводы владельца (заполнить самостоятельно):** что ещё пришлось уточнить в постановке задачи и насколько полезным оказался результат.

## Релизы

Используйте [Conventional Commits](https://www.conventionalcommits.org/): `feat: ...`, `fix: ...`, `chore: ...`; для несовместимых изменений — `feat!: ...`. Workflow `.github/workflows/release-please.yml` на ветке `main` поддерживает release-PR, changelog и версии. В настройках репозитория GitHub включите **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests**. Для запуска CI на автоматически созданных release-PR добавьте секрет `RELEASE_PLEASE_TOKEN` (fine-grained PAT с доступом к Contents и Pull requests); без него action использует `GITHUB_TOKEN`, но созданные им PR сами не запустят другие workflow.

Новые компоненты shadcn/ui можно добавлять через `npx shadcn@latest add <имя>`; CLI не установлен как зависимость приложения.

## О Хекслете

[Хекслет](https://ru.hexlet.io/) — школа программирования: авторские программы обучения с практикой, поддержкой наставников и реальными проектами, которые остаются в резюме. Этот репозиторий — один из таких проектов.
